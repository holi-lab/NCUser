Non-Collaborative User Simulators for Tool Agents

Jeonghoon Shim, Woojung Song, Cheyon Jin, Seungwon Kook, Yohan Jo†

Graduate School of Data Science, Seoul National University

† Corresponding author

Paper arXiv OpenReview Code Models BibTeX

TL;DR

Tool agents are trained and tested against user simulators that always cooperate. We build a simulator that behaves the way real users sometimes do, asking for things the agent cannot do, drifting off topic, losing patience, and typing half-sentences, while still delivering every piece of information the task needs. State-of-the-art agents degrade under every one of these behaviors, and fine-tuning on collaborative data alone does not fix it.

Five questions, answered on MultiWOZ and τ-bench with five agent LLMs:

  1. Which behaviors? What do non-collaborative users actually do? Four things, grounded in marketing research and real user–LLM chat logs: request an unavailable service, go off on a tangent, show impatience, and send incomplete utterances.
  2. How to simulate them without losing the goal? A collaborative backbone with a dialogue state tracker and an ending verifier, plus one LLM module per behavior. Only 3.0% of simulated dialogues miss a goal item on the first attempt, and those are regenerated.
  3. How much do agents suffer? Every model drops. Tangential users cost the most (29.1% relative success on average), each behavior breaks agents in its own way, and even GPT-4.1-mini loses up to 17 points when two behaviors co-occur.
  4. Does fine-tuning help? Collaborative-only SFT lifts 3B models above 90% on collaborative users but leaves the unavailable-service and incomplete-utterance modes 15 to 30 points behind. Adding non-collaborative dialogues raises the average from 78.8 to 86.9.
  5. Is the simulator realistic? It is harder on agents than a prompt-only simulator at the same goal alignment, and human annotators prefer its dialogues in about 70% of pairwise comparisons.

Pick a benchmark and a metric: each group is one agent LLM, each bar one user mode. Relative SR divides by the collaborative score, so bars below the dashed line are losses caused by the behavior.

Four non-collaborative behaviors

We surveyed customer types from marketing research and user types from studies of user–LLM conversations, kept the ones that show up inside a dialogue, and clustered them into four categories. Each card gives the definition, an example, and how the simulator produces it.

Unavailable service

Requests that no available API can fulfil, because the API is missing or lacks the needed parameter.

Users do not know where the agent's boundaries are, so they ask for things it cannot do.

Book me a window seat on the train.The train-booking API has no seat option, so the agent has to decline or set the request aside.

Simulated by GPT-4.1-mini reading the API documentation and the user goal, then writing three extra goal sentences that need a missing API or an unsupported parameter. They are appended to the original goal.

Tangential

Utterances unrelated to the task, typically personal interests or background, and complaints when the agent ignores them.

Factual questionOpinion questionGeneral opinionNon-opinion statement
By the way, where do you think I should visit first traveling in NA?Asked in the middle of a train booking. If the agent presses on with the transaction, the user feels unheard.

Simulated by sampling a persona from Persona Hub, having GPT-4o-mini write a tangential utterance in one of the four dialogue acts, and merging it with the collaborative utterance. A checker tests whether the agent responded; if not, a complaint replaces or augments the next turn.

Impatience

Emotional reactions when the agent takes too long or keeps failing, escalating over the dialogue.

Belligerent abuseThreatUrge
Stop wasting my time and just get it done!After a booking attempt fails again.

Simulated by two triggers: the agent reports a failure (detected by GPT-4.1-mini), or all goal information has been given and the task is still unresolved (from the state tracker). Anger fires with a probability that starts at 0.5 and rises by 0.1 per trigger; once expressed, the user stays cynical for the rest of the dialogue.

Incomplete utterances

Poorly articulated messages: extremely brief ones, or ones sent before they were finished.

Least-effort typing, as seen throughout LMSYS and WildChat conversations.

Book train, 2  ·  I want to resBoth stand for “I want to reserve a train for 2 people.”

Simulated by style transfer with five real brief messages as few-shot examples, or by cutting the collaborative utterance at a random point. The state tracker marks truncated information as unsent so it is delivered later.

A simulator that misbehaves but still finishes the job

A non-collaborative simulator is only useful if the agent's failures are the agent's fault. Every behavior above is layered on a collaborative simulator that is built to deliver the whole user goal, so a failed task means the agent could not cope, not that the user forgot to mention something.

Collaborative backbone

The backbone is the prompt-based simulator of τ-bench, run with GPT-4.1-mini. It reads the user goal, an instruction, and the dialogue history, and emits <END> when it thinks the task is done. Two LLM modules keep it goal-aligned:

  • Dialogue state tracker. The user goal is sharded into information pieces. The tracker records which pieces have been conveyed at each turn and, if the simulator tries to stop with pieces left over, delivers the rest before ending.
  • Ending verifier. Blocks <END> when the agent still has to act or is waiting for the user's confirmation, so the agent is never denied the chance to complete the booking.

After every simulation, GPT-4o-mini checks goal alignment: whether every piece of information and intent in the user goal was communicated. Misaligned dialogues are regenerated. Across 1,230 dialogues spanning the collaborative and the four non-collaborative modes, only 37 (3.0%) failed this check on the first attempt, and the judge agrees with a human annotator at a Matthews correlation of 0.77 on 40 sampled dialogues.

Evaluation setup

MultiWOZRestaurant, hotel, taxi, and train bookings. We built a new agent environment with 11 APIs, including AppWorld-style helper APIs that the agent must call to discover API documentation. 89 test scenarios that require bookings across multiple domains.

AgentReAct, reasoning before each action, with a 30-step limit per dialogue. Five LLMs: GPT-4.1-mini, GPT-4.1-nano, Qwen3-235b-a22b, Qwen3-30b-a3b, Llama-3.1-70b-instruct.
MetricSuccess rate (SR): the final database state exactly matches the ground truth. Averaged over 4 trials per scenario, so 356 simulations per mode on MultiWOZ and 628 on τ-bench.

Unavailable service immature tool use

Agents re-fetch API documentation they already have. When a request cannot be served, most agents repeatedly call the helper APIs that return documentation, as if searching for a solution that does not exist. On MultiWOZ, duplicated helper calls per dialogue jump for GPT-4.1-mini, GPT-4.1-nano, and Llama-3.1-70b. For GPT-4.1-nano these redundant calls eat the 30-step budget: the share of dialogues that hit the limit rises from 15% to 26%.

The Qwen models avoid the duplication, but they diverge: Qwen3-30b-a3b keeps 97.7% of its success rate, while Qwen3-235b-a22b falls to 80.2% because it starts fabricating API results instead of calling the API. Its hallucinated results per dialogue go from 0.33 in the collaborative mode to 1.13.

Tangential dialogue management

The most damaging behavior: 29.1% relative success lost on average. Agents that juggle an off-topic thread increasingly fail to do the core task at all. “No book” errors on MultiWOZ and “no ground-truth API” errors on τ-bench both rise in this mode for every model.

GPT-4.1-nano falls the furthest (to 41.5% of its collaborative score on MultiWOZ) because it triggers the most user complaints: it ignores the tangent, the simulator complains, and the exchange repeats until the 30-step limit is exhausted. The share of its MultiWOZ dialogues that run out of steps goes from 15% to 44%.

Impatience dialogue management

Agents apologize instead of acting, and the ones that apologize most lose most. Impatience is the mildest behavior overall; GPT-4.1-mini holds its score on both benchmarks. But every model multiplies its apology utterances when the user gets angry, a habit that likely comes from preference training. Under a 30-step budget, apologizing delays task completion and provokes more anger, a negative feedback loop. Llama-3.1-70b, Qwen3-30b-a3b, and Qwen3-235b-a22b have the highest apology ratios and, in that order, the largest losses.

Incomplete utterances immature tool use

Terse users make agents invent API parameters, but only where documentation must be looked up. MultiWOZ suffers far more than τ-bench in this mode. The difference is API access: τ-bench puts the full documentation in the system prompt, while MultiWOZ agents must fetch it through helper APIs. On MultiWOZ, calls with undocumented parameter keys rise for every model when utterances are brief or cut off; on τ-bench they stay near zero. Qwen3-30b-a3b even improves on τ-bench (107.9% relative SR) while losing almost half its score on MultiWOZ.

Model size is not robustness

GPT-4.1-mini is the most robust model and beats GPT-4.1-nano on relative SR under every behavior. Within the Qwen family, though, there is no clean size effect: the 235B model is more resilient in some modes and the 30B model in others, depending on the behavior and benchmark. Size alone does not predict how an agent handles a difficult user.

Two behaviors at once

Even the most robust agent breaks when behaviors co-occur. Real users rarely misbehave in only one way. Pairing behaviors costs GPT-4.1-mini up to 16.6 points on MultiWOZ (tangential + incomplete) and 11.7 points on τ-bench (impatient + tangential), losses several times larger than under any single behavior. The full comparison against a prompt-only simulator is in the simulator quality section.

Beyond tool use: ColBench and MINT

The simulator ports to other dialogue settings with small adjustments. On ColBench backend programming, which involves no external tools, the pattern matches the tool-agent results: GPT-4.1-mini is the most robust and the tangential and incomplete modes hurt most. On MINT HotpotQA, where the user and agent collaborate on a problem, no such trend appears, and Qwen3-30b-a3b, robust to unavailable services everywhere else, degrades there. Domains built around fulfilling a user goal behave alike; domains with a different interaction structure do not.

Fine-tuning on collaborative data leaves agents fragile

Practitioners typically fine-tune a small model on their own task data, and that data comes from cooperative users. We fine-tuned Llama-3.2-3b-instruct, Qwen2.5-3b-instruct, and Qwen2.5-7b-instruct (QLoRA) on successful MultiWOZ dialogues between GPT-4.1-mini and the collaborative simulator.

The gains do not transfer. Zero-shot, these models succeed under 4% of the time; after fine-tuning they exceed 90% with collaborative users. Under non-collaborative users the improvement lags, worst for unavailable services (61 to 77%) and incomplete utterances (72 to 82%). The fine-tuned agents make more duplicated helper API calls in the unavailable-service mode and more parameter hallucinations in the incomplete-utterance mode than the zero-shot baselines did.

Adding non-collaborative dialogues to the training set

Mixing in dialogues from the four non-collaborative modes in equal proportion (“uniformly weighted”) lifts Qwen2.5-3b-instruct on every behavior and raises the average from 78.8 to 86.9, with the biggest jump on unavailable services. Up-weighting the incomplete-utterance data closes that mode's gap further but costs a little elsewhere, so the average is unchanged. Uniform weighting is a reasonable default; up-weight a behavior when a minimum service level must hold for that kind of customer.

Is the simulator itself any good?

A non-collaborative simulator should be hard on agents, still convey the whole goal, and read as natural. We compare against a prompt-based user simulator (PBUS), which follows τ-bench's prompt-only approach and simply adds the behavior descriptions to the prompt, with no extra modules. The comparison uses the harder setting of two behaviors at once.

Difficulty and goal alignment

PBUS barely moves the agent; ours does, at the same or better goal alignment. Under PBUS, GPT-4.1-mini's success rate changes little across behavior pairs. Under our simulator it drops consistently. Initial goal alignment (IGA), the share of dialogues that convey every goal item on the first attempt, is comparable on MultiWOZ and higher on τ-bench, so the extra difficulty comes from the behaviors, not from a user who forgot to say something.

Takeaways

  • Test your agent against users who do not cooperate. A collaborative simulator hides failure modes that appear the moment a user asks for the impossible, changes the subject, gets angry, or types “I want to res”.
  • Each behavior needs its own fix. Unavailable services and incomplete utterances call for better grounding in API documentation; tangents and impatience call for dialogue strategies that acknowledge the user without stalling the task.
  • Put non-collaborative dialogues in the training set. Collaborative-only SFT makes small agents look ready and leaves them fragile; a uniform mix of the four behaviors recovers most of the gap.
  • Goal alignment is what makes a hard simulator trustworthy. A state tracker and an ending verifier are enough to keep a misbehaving user from forgetting the task, so failures can be attributed to the agent.

Run the simulator on your own agent

The repository ships both environments with separate conda setups. Behaviors are switched on by dropping YAML files into non_coll_list/; models, trial counts, and vLLM serving are set in the run script. Live runs need an OpenAI key (simulator and judge modules) and an OpenRouter key for the open-weight agents.

# MultiWOZ environment
git clone https://github.com/holi-lab/NCUser
cd NCUser/multiwoz_env
conda create -n multiwoz_env python=3.11 && conda activate multiwoz_env
pip install -r requirements.txt

# choose the user behaviors to simulate (any subset; each YAML is one mode):
#   normal (collaborative) · unavailable_service · tangential
#   emotional_acts (impatience) · fragment_dumping (incomplete utterance)
cp non_coll_normal.yaml non_coll_tangential.yaml non_coll_list/

# set N (trials), the models array, and API keys in run_dialogue_simulation.sh, then
./run_dialogue_simulation.sh
./run_error_analysis.sh

# τ-bench environment: same workflow
cd ../tau_env && conda create -n tau_env python=3.11 && conda activate tau_env
pip install -e .
./run_dialogue_simulation.sh

Fine-tuned agents (holi-lab/qwen-2.5-3b-multiwoz-finetuned and others) and the MultiWOZ training sets are on Hugging Face; all dialogue logs behind the tables above are on Google Drive. The README covers configuration, vLLM serving, and training.
